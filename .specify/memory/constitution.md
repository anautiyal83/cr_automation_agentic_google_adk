# CR Automation Agentic Constitution

## Core Principles

### I. Config-Driven, Zero-Code Use Cases

Every new use case (UC) MUST be handled entirely through YAML
configuration files and optional Python scripts. No Java code
changes, no recompilation, and no redeployment of the core
framework are permitted to onboard a new UC. The three mandatory
artifacts per UC are:

- **Validation Rules YAML** — field-level and cross-field
  validation constraints
- **JSON Template YAML** — the canonical JSON payload structure
  for the target system
- **Workflow YAML** — ordered steps for CIQ processing,
  CLI command assembly, and execution

Optional Python scripts MAY supplement a UC for transformation
logic that cannot be expressed declaratively in YAML.

**Rationale:** The framework's value proposition is eliminating
per-UC engineering effort; any code change defeats that purpose.

### II. LLM-Agent-Generated Configs

All three YAML configs (and optional Python scripts) MUST be
generated by LLM agents from UC requirement documents. Human
editing is permitted only to correct agent output after review,
never as the primary authoring path.

- Agents MUST receive the UC requirement document as input.
- Agents MUST produce syntactically valid YAML that conforms to
  the framework's schema.
- Agent prompts and chains MUST be versioned alongside the
  framework source.

**Rationale:** Manual config authoring does not scale and
reintroduces the bottleneck the agentic layer is designed to
remove.

### III. Automated Test-and-Retry Loop (NON-NEGOTIABLE)

Generated configs MUST be automatically tested against real CIQ
data and a mock simulator before being accepted. On failure, the
framework MUST retry by feeding error feedback back to the LLM
agent for correction. This loop MUST operate without human
intervention for at least N configurable retry cycles.

- The test harness MUST execute validation rules against CIQ
  sample data.
- The mock simulator MUST exercise the workflow end-to-end
  (CLI command generation, execution, response parsing).
- Each retry cycle MUST include the previous failure's error
  message and context in the agent prompt.

**Rationale:** Unattended generation is only trustworthy when
paired with unattended verification and self-correction.

### IV. CIQ Data Integrity

CIQ (Customer Installation Questionnaire) data is the
authoritative input to the system. Processing MUST preserve data
fidelity at every stage:

- The ciq-processor module MUST parse CIQ documents without
  lossy transformations.
- Validation rules MUST reject malformed or incomplete CIQ
  records with actionable error messages.
- No downstream step (JSON template population, CLI command
  assembly) MAY silently drop or alter CIQ field values.

**Rationale:** Garbage-in-garbage-out failures in telecom
provisioning are expensive; data integrity is non-negotiable.

### V. Deterministic Test Reporting

Every test execution MUST produce both an HTML report and an
MS Excel report. Reports MUST include:

- Per-step pass/fail status with timestamps
- Actual vs. expected values for every assertion
- Full error traces on failure
- CIQ input data used in the test run

Reports MUST be generated regardless of overall pass/fail
outcome. Report format and content MUST be consistent across UCs.

**Rationale:** Stakeholders (operations, QA, delivery) rely on
these reports for go/no-go decisions; inconsistent or missing
reports block release.

### VI. Layered Architecture Integrity

The framework is built on top of the existing cr-automation Java
framework (modules: ciq-processor, cli-automation-standalone).
The agentic layer MUST NOT modify, fork, or bypass the core
framework modules.

- ciq-processor: CIQ parsing and data extraction — consumed
  as-is by the agentic layer.
- cli-automation-standalone: CLI command execution engine —
  invoked via its existing API/CLI interface.
- The agentic layer owns: agent orchestration, YAML schema
  definitions, test harness, retry logic, and report generation.

**Rationale:** Maintaining a clean boundary ensures the core
framework remains stable and independently releasable.

### VII. Simplicity and YAGNI

Favor the simplest design that satisfies current requirements.
Do not build abstractions, plugin systems, or configurability
beyond what is needed today.

- A new agent capability MUST be justified by a concrete UC
  requirement, not a hypothetical future need.
- YAML schema extensions MUST be motivated by a real field or
  workflow step, not speculative generality.

**Rationale:** Over-engineering an agentic system compounds
complexity; each unnecessary abstraction increases prompt
fragility and maintenance burden.

## Technology & Architecture Constraints

- **Core framework language:** Java (ciq-processor,
  cli-automation-standalone). No changes to core Java modules
  from the agentic layer.
- **Agentic layer language:** Python (agent orchestration,
  test harness, report generation, optional UC scripts).
- **Config format:** YAML exclusively for UC definitions;
  JSON for runtime payloads produced from templates.
- **LLM integration:** Agent prompts and model configuration
  MUST be externalized (not hard-coded) so models can be
  swapped or updated without code changes.
- **Test data:** Real CIQ samples MUST be stored in a
  dedicated test-data directory, version-controlled, and
  never committed with PII unless redacted.
- **Reports:** HTML and MS Excel (.xlsx) formats are mandatory
  outputs of every test run.

## Development Workflow & Quality Gates

- **UC onboarding flow:** Requirement doc received, agent
  generates configs, automated tests execute, retry loop runs
  on failure, reports produced, human reviews reports and
  configs, UC is accepted or feedback is provided.
- **Config schema validation:** Every YAML config MUST pass
  schema validation before test execution. Schema files are
  the single source of truth for config structure.
- **Mock simulator parity:** The mock simulator MUST be kept
  in sync with the real target system's CLI interface. Any
  divergence MUST be tracked as a known limitation.
- **Version control:** All configs (generated and reviewed),
  agent prompts, schemas, and test data MUST be committed to
  the repository. Generated artifacts MUST NOT be .gitignored.

## Governance

This constitution is the highest-authority document for the
cr_automation-agentic project. All design decisions, code
reviews, and architecture changes MUST comply with the
principles defined here.

- **Amendments** require: (1) a written proposal describing the
  change and its rationale, (2) review and approval by the
  project lead, (3) an updated constitution with incremented
  version, and (4) a migration plan if the amendment affects
  existing UCs or configs.
- **Versioning** follows semantic versioning: MAJOR for
  principle removals or redefinitions, MINOR for new
  principles or material expansions, PATCH for clarifications
  and wording fixes.
- **Compliance review:** Every PR that modifies framework
  architecture, agent behavior, or config schemas MUST
  reference the relevant constitution principle(s) in its
  description.
- **Guidance file:** Use `.specify/memory/constitution.md` as
  the living governance reference for development decisions.
